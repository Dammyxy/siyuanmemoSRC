# 持久化策略分析 - 单文件 vs 分文件存储

## 问题

持久化方面要不要分开存储 Xiuyuan 和 Card 数据？

## 当前方案：单文件存储

### 现状

```typescript
// UnifiedCardStore
{
  version: 1,
  xiuyuans: {
    "xy_123": { /* Xiuyuan 数据 */ },
    "xy_456": { /* Xiuyuan 数据 */ }
  },
  cardDTOs: {
    "card_789": { /* Card 数据 */ },
    "card_101": { /* Card 数据 */ }
  }
}
```

**文件**：`data/storage/unified-cards.msgpack`

### 优点

1. **原子性保证**
   - 单个文件的读写是原子操作
   - Xiuyuan 和 Card 的一致性由文件系统保证
   - 不会出现"Xiuyuan 保存了但 Card 没保存"的情况

2. **简单的事务模型**
   - 一次保存操作完成所有数据的持久化
   - 不需要复杂的两阶段提交
   - 回滚简单（恢复单个文件）

3. **加载性能好**
   - 一次 I/O 操作加载所有数据
   - MessagePack 解析速度快
   - 适合启动时全量加载

4. **备份和恢复简单**
   - 单个文件包含所有数据
   - 备份：复制一个文件
   - 恢复：替换一个文件

5. **数据迁移容易**
   - 版本升级只需要处理一个文件
   - 数据格式转换在内存中完成

### 缺点

1. **写放大问题**
   - 更新一张卡片需要重写整个文件
   - 文件越大，写入越慢
   - 频繁更新时性能下降

2. **内存占用**
   - 需要将整个文件加载到内存
   - 对于大量卡片（10万+）可能占用较多内存

3. **并发写入风险**
   - 多个进程同时写入会导致数据损坏
   - 需要文件锁机制

4. **部分更新困难**
   - 无法只更新 Card 数据而不加载 Xiuyuan
   - 无法增量保存

## 备选方案：分文件存储

### 方案 A：按类型分文件

```
data/storage/
├── xiuyuans.msgpack      # 所有 Xiuyuan 数据
└── cards.msgpack         # 所有 Card 数据
```

**优点**：
- 可以独立更新 Card 数据
- 减少写放大（只重写 cards.msgpack）

**缺点**：
- 失去原子性保证
- 需要两次 I/O 操作
- 一致性问题：Xiuyuan 保存了但 Card 保存失败

### 方案 B：按 Xiuyuan 分文件

```
data/storage/
├── xiuyuan-xy_123.msgpack
│   ├── xiuyuan: { /* Xiuyuan 数据 */ }
│   └── cards: [ /* 该 Xiuyuan 的所有 Cards */ ]
├── xiuyuan-xy_456.msgpack
└── index.msgpack          # 索引文件
```

**优点**：
- 保持聚合的原子性
- 更新一个 Xiuyuan 不影响其他
- 支持按需加载（懒加载）

**缺点**：
- 文件数量多（N 个 Xiuyuan = N 个文件）
- 全局查询需要读取多个文件
- 索引维护复杂

### 方案 C：混合存储（推荐）

```
data/storage/
├── unified-cards.msgpack  # 主数据文件（当前方案）
└── wal/                   # Write-Ahead Log（可选）
    ├── 001.wal
    └── 002.wal
```

**优点**：
- 保持单文件的优点
- WAL 提供增量更新能力
- 崩溃恢复能力强

**缺点**：
- 实现复杂度增加
- 需要 WAL 压缩机制

## DDD 视角分析

### 聚合根的持久化原则

**DDD 建议**：
> 聚合根应该作为一个整体进行持久化和加载

**应用到你的场景**：
- Xiuyuan 是聚合根
- Card 是聚合内的实体
- 理论上应该一起持久化

### 但是...性能优化是合理的

**Eric Evans（DDD 作者）的观点**：
> 在性能要求下，可以将聚合的部分数据分离存储，
> 但要保持聚合的逻辑完整性

**你的情况**：
- 卡片数量可能很大（10万+）
- 查询模式：经常查询单个 Card，不需要加载整个 Xiuyuan
- 分离存储是合理的性能优化

## 性能对比

### 场景 1：启动加载（10万张卡片）

| 方案 | 文件数 | I/O 次数 | 加载时间 | 内存占用 |
|------|--------|----------|----------|----------|
| 单文件 | 1 | 1 | ~2s | ~50MB |
| 分文件（按类型） | 2 | 2 | ~2.5s | ~50MB |
| 分文件（按 Xiuyuan） | 1000+ | 1000+ | ~10s+ | ~50MB |

**结论**：单文件最快

### 场景 2：更新单张卡片

| 方案 | 写入大小 | 写入时间 | 风险 |
|------|----------|----------|------|
| 单文件 | 50MB | ~500ms | 写放大 |
| 分文件（按类型） | 40MB | ~400ms | 一致性 |
| 分文件（按 Xiuyuan） | 50KB | ~5ms | 索引维护 |

**结论**：按 Xiuyuan 分文件最快，但复杂度高

### 场景 3：查询到期卡片

| 方案 | 需要加载 | 查询时间 |
|------|----------|----------|
| 单文件 + 内存索引 | 全部（启动时） | <1ms |
| 分文件（按类型） + 内存索引 | 全部（启动时） | <1ms |
| 分文件（按 Xiuyuan） | 按需 | ~100ms |

**结论**：内存索引方案最快

## 实际使用模式分析

### 你的应用特点

1. **启动时全量加载**
   - 需要构建内存索引
   - 支持快速查询

2. **运行时频繁查询**
   - 查询到期卡片
   - 按 blockId、xiuyuanId、type 查询
   - 都是内存操作，不涉及磁盘 I/O

3. **更新频率**
   - 评分后更新卡片（高频）
   - 创建/删除卡片（低频）
   - 使用防抖保存（1秒延迟）

4. **数据规模**
   - 预期：1000-10000 张卡片（大多数用户）
   - 极限：100000 张卡片（重度用户）

### 性能瓶颈分析

**当前方案的瓶颈**：
- ✅ 启动加载：2s（可接受）
- ✅ 查询性能：<1ms（优秀）
- ⚠️ 保存性能：500ms（可接受，但有优化空间）

**保存性能优化**：
- 当前：防抖 1 秒 + MessagePack 序列化
- 瓶颈：序列化 + 文件写入
- 优化方向：
  1. 增量序列化（只序列化变更的部分）
  2. 压缩（减少文件大小）
  3. 异步写入（不阻塞主线程）

## 推荐方案

### 🎯 保持单文件存储（当前方案）

**理由**：

1. **性能已经足够好**
   - 启动加载 2s（10万卡片）
   - 查询 <1ms（内存索引）
   - 保存 500ms（防抖后不频繁）

2. **简单可靠**
   - 原子性保证
   - 一致性保证
   - 备份恢复简单

3. **符合你的使用模式**
   - 启动时全量加载
   - 运行时内存操作
   - 保存时批量写入

4. **DDD 合规**
   - 虽然 Xiuyuan 和 Card 在文件内分开
   - 但作为一个整体持久化
   - 保持了聚合的完整性

### 可选优化：增量保存（未来）

如果保存性能成为瓶颈，可以考虑：

```typescript
class UnifiedStorageManager {
  private dirtyXiuyuans: Set<string> = new Set();
  private dirtyCards: Set<string> = new Set();
  
  async save(): Promise<Result<void>> {
    // 只序列化变更的数据
    const changedData = {
      xiuyuans: this.getChangedXiuyuans(),
      cardDTOs: this.getChangedCards()
    };
    
    // 增量写入（使用 WAL 或 delta 文件）
    await this.persistence.saveIncremental(changedData);
    
    // 定期合并（压缩）
    if (this.shouldCompact()) {
      await this.persistence.compact();
    }
  }
}
```

**优点**：
- 减少序列化开销
- 减少写入大小
- 保存更快

**缺点**：
- 实现复杂
- 需要 WAL 或 delta 机制
- 需要定期压缩

## 对比其他应用

### Anki（间隔重复软件）

**存储方案**：SQLite 数据库
- 单文件存储
- 支持事务
- 支持索引查询

**优点**：
- 成熟稳定
- SQL 查询灵活
- 支持增量更新

**缺点**：
- 依赖 SQLite
- 序列化开销
- 文件格式不透明

### SuperMemo（间隔重复软件）

**存储方案**：自定义二进制格式
- 单文件存储
- 内存映射文件
- 增量更新

**优点**：
- 性能极致
- 支持大规模数据

**缺点**：
- 实现复杂
- 平台依赖
- 调试困难

### 你的方案（MessagePack）

**优点**：
- 简单易懂
- 跨平台
- 人类可读（通过工具）
- 性能足够好

**缺点**：
- 不支持增量更新（当前）
- 写放大（大文件时）

## 最终建议

### 持久化策略

```
✅ 单文件存储（MessagePack）
   ├─ xiuyuans: Record<string, IXiuyuan>
   └─ cardDTOs: Record<string, CardPersistenceDTO>

✅ 内存索引（快速查询）
   ├─ indexByBlockID
   ├─ indexByXiuyuanID
   ├─ indexByType
   └─ indexByDue

✅ 防抖保存（1秒延迟）
   └─ 减少写入频率

❌ 不需要分文件存储
   └─ 增加复杂度，收益不明显
```

### 数据组织

```
✅ Xiuyuan 和 Card 在文件内分开
   └─ 便于查询和索引

✅ 移除 meta.cards 冗余
   └─ 只保留 meta.cardIds

✅ Card 数据只存储在 cardDTOs
   └─ 单一数据源
```

### 总结

**不需要分开存储文件**，当前的单文件方案已经很好：
- ✅ 性能足够
- ✅ 简单可靠
- ✅ 符合 DDD
- ✅ 易于维护

**只需要修复数据冗余问题**（移除 `meta.cards`），不需要改变持久化策略。
